# ChoreTUI Development Specification

Status: baseline for MVP implementation  
Owner issue: #1  
Decision date: 2026-09-12

## 1. Product definition

ChoreTUI is a local, keyboard-driven terminal application for defining recurring household chores, seeing their occurrences on an ISO-week board, and recording completion. It is designed for one person on one machine. The application must start quickly, work offline, and keep historical results stable when a chore is later edited.

### Primary use cases

1. Open the application and immediately see the current ISO week.
2. Inspect all chores due in that week and move the selection by chore, day, or week.
3. Toggle an occurrence between pending and completed.
4. Add and edit recurring chore definitions.
5. Disable a chore temporarily or delete it without erasing its history.
6. Review completed, pending, and missed counts for a week.
7. Diagnose configuration and database problems without opening the TUI.

### Core workflow

On startup, ChoreTUI resolves its configuration and database locations, applies compatible database migrations, materializes occurrences needed for the current week, and opens the Weekly Board. The current day is selected when it contains chores; otherwise the nearest day with a chore is selected. The user navigates with arrow keys or Vim-style keys, toggles completion with `Space`, opens an editor with `a` or `e`, and changes weeks with `[` and `]`. Mutations are committed immediately. There is no separate save command for the board.

### Terminology

- **Chore**: the stable user-facing identity, such as “Vacuum”.
- **Schedule**: a versioned recurrence rule for a chore.
- **Occurrence**: one dated instance generated by a schedule.
- **Nominal date**: the date produced by recurrence calculation; it never changes.
- **Due date**: the displayed date; initially the nominal date and later usable for a one-off move.
- **Pending**: an occurrence that has not been completed or skipped.
- **Completed**: an occurrence with a completion timestamp.
- **Missed**: a derived display state for a pending occurrence whose due date is before today.
- **Disabled**: a chore that produces no occurrences until it is re-enabled.
- **Deleted**: a soft-deleted chore hidden from management views by default; its history remains.
- **Week**: an ISO 8601 week, identified as `YYYY-Www`.

### MVP

- Weekly Board with responsive layouts.
- ISO-week and day navigation.
- Add, edit, enable, disable, and soft-delete chores.
- Recurrence rules: weekly, every N weeks, every N days, and monthly.
- Multiple weekdays for weekly rules.
- On-demand, idempotent occurrence generation.
- Pending/completed state and derived missed state.
- Weekly completed, total, percentage, and missed statistics.
- SQLite persistence and forward-only migrations.
- TOML configuration with a deliberately small option set.
- In-app help plus `--help`, `--version`, and `doctor` CLI commands.
- Structured local logs suitable for diagnosis.

### Deferred features

- Moving or skipping a single occurrence. The schema and domain API reserve these operations, but MVP screens do not expose them.
- Weekly streaks and multi-week charts.
- Headless add/edit/list commands.
- Import/export, built-in backup scheduling, notifications, themes, localization, and mouse control.
- Editing historical occurrences or retrospectively applying a new schedule.

### Non-goals

- Accounts, cloud sync, sharing, multi-user conflict resolution, or network dependencies.
- A general calendar or RFC 5545 recurrence engine.
- Times of day, time zones per chore, durations, reminders, dependencies, priorities, tags, or subtasks.
- Mobile or graphical interfaces.
- Hard deletion of historical data from the interactive application.

## 2. Domain model

All identifiers are UUID v7 strings. Calendar dates are ISO `YYYY-MM-DD` text. Timestamps are UTC RFC 3339 strings with second precision. Weekdays use ISO numbers `1` (Monday) through `7` (Sunday). User-facing calculations use the machine's current local date; no time-of-day scheduling exists.

### Chore

| Field | Type | Required | Rules |
|---|---|---:|---|
| `id` | UUID v7 | yes | Stable across schedule revisions. |
| `name` | string | yes | Trimmed, 1–80 Unicode scalar values. |
| `description` | string | no | Trimmed, maximum 1,000 scalar values. |
| `enabled` | boolean | yes | Current generation state. |
| `created_at` | timestamp | yes | Immutable. |
| `updated_at` | timestamp | yes | Updated on user-visible changes. |
| `deleted_at` | timestamp | no | Soft deletion marker. |

Names need not be unique. The UI disambiguates identical names through descriptions and scheduled days. Deleting a chore sets `deleted_at`, disables it, closes its active schedule, and retains occurrences.

### Schedule

| Field | Type | Required | Rules |
|---|---|---:|---|
| `id` | UUID v7 | yes | Identifies one immutable schedule revision. |
| `chore_id` | UUID v7 | yes | References the stable chore. |
| `kind` | enum | yes | `weekly`, `daily_interval`, or `monthly`. |
| `interval` | integer | yes | `1..999`; monthly MVP uses `1`. |
| `anchor_date` | date | yes | Defines recurrence phase. |
| `monthly_day` | integer | conditional | Required only for monthly; `1..31`. |
| `valid_from` | date | yes | Inclusive. |
| `valid_until` | date | no | Inclusive; null means active. |
| `created_at` | timestamp | yes | Immutable. |

Weekly schedules have one or more rows in `schedule_weekdays`. Other kinds have none. Schedule rows are immutable after creation except for closing `valid_until`. Editing recurrence closes the active schedule on the day before the new effective date and creates a replacement. In MVP, edits are effective today. In the same transaction, pending occurrences from the replaced schedule with `due_date >= today` are removed and then regenerated from the new schedule when needed. Completed, skipped, or past occurrences are historical and never rewritten. Renaming a chore similarly updates only pending occurrences due today or later; historical snapshots remain unchanged.

Disabling closes the active schedule yesterday. If that would precede its `valid_from`, `valid_until` is set to `valid_from` while the disabled chore suppresses generation for that date. Pending occurrences due today or later are removed in the same transaction. Re-enabling creates a new equivalent schedule with `valid_from` and `anchor_date` set to today, so the disabled interval is not backfilled.

### Occurrence

| Field | Type | Required | Rules |
|---|---|---:|---|
| `id` | UUID v7 | yes | Stable occurrence identity. |
| `chore_id` | UUID v7 | yes | Historical link to the chore. |
| `schedule_id` | UUID v7 | yes | Schedule revision that produced it. |
| `nominal_date` | date | yes | Immutable generated date. |
| `due_date` | date | yes | Initially equal to nominal date. |
| `name_snapshot` | string | yes | Chore name at materialization time. |
| `description_snapshot` | string | no | Description at materialization time. |
| `state` | enum | yes | `pending`, `completed`, or `skipped`. |
| `completed_at` | timestamp | conditional | Present only when completed. |
| `created_at` | timestamp | yes | Materialization timestamp. |
| `updated_at` | timestamp | yes | Last state/override change. |

`(schedule_id, nominal_date)` is unique, making materialization idempotent. Completion is stored on the occurrence, never on the chore. A `pending` occurrence with `due_date < today` is displayed and counted as missed; “missed” is not persisted. Toggling a completed occurrence returns it to pending and clears `completed_at`. `skipped` and a changed `due_date` are reserved for post-MVP occurrence overrides.

## 3. Recurrence semantics

The recurrence engine is a pure domain service with input `(schedule, inclusive date range)` and output as an ordered, duplicate-free set of nominal dates. It neither reads SQLite nor knows about TUI state.

### Weekly and every N weeks

`kind = weekly`. `anchor_date` determines ISO anchor week. A candidate date matches when:

1. its weekday is present in `schedule_weekdays`; and
2. the signed number of ISO weeks from the Monday of the anchor week to the Monday of the candidate week is non-negative and divisible by `interval`.

`interval = 1` is weekly; larger values mean every N calendar weeks. This remains correct across ISO week-year boundaries. Multiple weekdays create separate occurrences belonging to the same schedule.

### Every N days

`kind = daily_interval`. A candidate matches when the signed whole-calendar-day distance from `anchor_date` is non-negative and divisible by `interval`. Calculation uses dates rather than 24-hour durations, so daylight-saving changes are irrelevant.

### Monthly

`kind = monthly`, `interval = 1`, and `monthly_day` is the desired day of month. If a month has fewer days, the occurrence falls on that month's final day. For example, day 31 becomes 28 February 2027 and 29 February 2028. The anchor month is the month containing `anchor_date`; candidates before `anchor_date` do not match. Supporting every N months is intentionally deferred, though the schema can later permit `interval > 1`.

### Validity, misses, and generation

- Generated dates are intersected with inclusive `valid_from`/`valid_until`.
- Disabled or deleted chores do not generate from an active schedule.
- Opening a week materializes that week in one transaction. Statistics and navigation may materialize other requested weeks the same way.
- A missed occurrence remains pending and visible in its original week indefinitely. It is not rolled forward and does not create another occurrence.
- Completing a missed occurrence is allowed and records the actual completion time.
- Schedule changes never update historical occurrences; pending occurrences due on or after the effective date are replaced transactionally.
- Reserved move behavior changes only `due_date`; recurrence and `nominal_date` remain unchanged. A moved occurrence appears in the week containing its due date and is excluded from its nominal week, without producing a duplicate.

## 4. Week model

- ISO 8601 weeks start Monday and end Sunday.
- Canonical identifiers use ISO week-year plus two-digit week: `2026-W37`.
- The title may render `Week 37 / 2026`; persistence and APIs use the canonical form.
- `[` and `]` subtract or add one ISO week using date arithmetic from the displayed Monday, not by incrementing a week number.
- `t` returns to the week containing the machine's current local date.
- Year boundaries are handled by the date library; for example, 31 December may belong to week 1 of the next ISO week-year.
- Historical occurrences remain queryable regardless of later chore edits, disables, or deletes.

## 5. TUI interaction model

### Global rules

- Exactly one screen or modal owns keyboard focus.
- Commands execute on a key press; no multi-key command grammar is used in MVP.
- `Esc` closes the top modal or cancels an editor with unsaved fields after confirmation.
- `?` opens contextual help. `q` quits from a non-modal screen; dirty editors require confirmation.
- Destructive actions require confirmation. Disabling does not.
- Successful board actions are reflected immediately and announced briefly in the status line. Errors remain visible until dismissed.

### Weekly Board

The board is the startup screen.

| Key | Action |
|---|---|
| `h` / `Left` | Select previous day. Wrap within the displayed week. |
| `l` / `Right` | Select next day. Wrap within the displayed week. |
| `j` / `Down` | Select next occurrence in the selected day. |
| `k` / `Up` | Select previous occurrence in the selected day. |
| `Space` | Toggle selected occurrence pending/completed. |
| `a` | Open Chore Editor in add mode, preselecting the selected weekday. |
| `e` | Edit the selected occurrence's chore. |
| `d` | Disable the selected occurrence's chore. |
| `D` | Soft-delete the selected occurrence's chore after confirmation. |
| `c` | Open Chore List. |
| `[` / `PageUp` | Previous week. |
| `]` / `PageDown` | Next week. |
| `t` | Current week. |
| `?` | Help. |
| `q` | Quit. |

When a day has no occurrence, `j`/`k` do nothing. Changing day selects its first pending occurrence, otherwise its first occurrence. Week changes preserve the weekday when possible and choose the nearest non-empty day only if the preserved day is empty.

### Chore Editor

The editor contains name, optional description, recurrence kind, interval where applicable, weekday multiselect for weekly schedules, monthly day for monthly schedules, and enabled state. `Tab`/`BackTab` moves focus, arrows change choices, `Space` toggles a weekday/checkbox, `Enter` activates the focused action, `Ctrl+S` saves, and `Esc` cancels. Inline validation prevents save and moves focus to the first invalid field. Editing recurrence is explicitly labeled “effective today”.

### Chore List

The list shows active chores by default, sorted case-insensitively by name and then creation time. `/` filters by name, `j`/`k` and arrows move, `Enter`/`e` edits, `Space` enables or disables, `D` soft-deletes with confirmation, `x` toggles display of deleted chores, `Esc` returns, and `?` opens help. Deleted chores are read-only in MVP.

### Help and confirmations

Help is a scrollable overlay grouped by current screen and global commands. `?`, `Esc`, or `q` closes it. Confirmation modals default to Cancel; `y` confirms, `n`/`Esc` cancels, and `Tab` plus `Enter` supports discoverable button navigation.

## 6. Weekly Board layout

The layout is selected on every terminal resize.

| Terminal size | Layout |
|---|---|
| width >= 110 and height >= 18 | Seven equal day columns in one row. |
| width 70–109 and height >= 20 | Two-row grid: Monday–Thursday, then Friday–Sunday. |
| width 40–69 and height >= 14 | One selected-day pane plus a compact seven-day week strip. |
| smaller than 40x14 | Too-small view with required and current dimensions; only resize, help, and quit operate. |

Each day header contains abbreviated weekday and day-of-month. Today uses an accent style; the selected day has a distinct border/style that remains distinguishable without color. Occurrences are vertically scrollable within a day. Scroll indicators show hidden items. Empty days display `No chores`.

An occurrence uses `[x]` when completed and `[ ]` when pending. Completed text is dimmed and may be struck through when supported. Missed occurrences use `!` plus an error style. The selected occurrence uses a leading cursor and reverse/bold style; meaning never depends on color alone. Narrow layouts truncate names with an ellipsis while preserving state markers.

The footer always shows canonical week, `Done: completed / total`, completion percentage rounded to the nearest whole number, and `Missed: n`. A second footer line shows context-sensitive key hints when height allows; otherwise `? Help` is retained. Total excludes skipped occurrences and includes all pending and completed occurrences due in the displayed week, including future days. A zero-total week displays `Completion: —` rather than `0%`.

## 7. Statistics

MVP statistics are intentionally limited to the displayed week:

- `total`: pending plus completed occurrences whose due date is in the week; skipped excluded.
- `completed`: occurrences in `completed` state.
- `missed`: pending occurrences with due date before today's local date.
- `completion percentage`: `completed / total * 100`, rounded half up; undefined for zero total.

The status is recomputed from persisted occurrences after each mutation. Weekly streak and history charts are deferred because their definitions and UI value should be validated after the core workflow ships.

## 8. Persistence

SQLite is the system of record. It offers transactional state changes, constraints, mature migration support, and a single local file that remains easy to inspect and back up.

### Locations

Using the `directories` crate and XDG conventions:

- configuration: `$XDG_CONFIG_HOME/choretui/config.toml`, defaulting to `~/.config/choretui/config.toml`;
- data: `$XDG_DATA_HOME/choretui/choretui.db`, defaulting to `~/.local/share/choretui/choretui.db`;
- logs: `$XDG_STATE_HOME/choretui/choretui.log`, defaulting to `~/.local/state/choretui/choretui.log`.

Explicit `CHORETUI_CONFIG` and `CHORETUI_DATA_DIR` environment variables override locations for testing and advanced use. Directories are created with user-only permissions where the platform supports it.

### Schema

```sql
CREATE TABLE schema_migrations (
  version INTEGER PRIMARY KEY,
  applied_at TEXT NOT NULL
);

CREATE TABLE chores (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL CHECK (length(trim(name)) BETWEEN 1 AND 80),
  description TEXT,
  enabled INTEGER NOT NULL CHECK (enabled IN (0, 1)),
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  deleted_at TEXT
);

CREATE TABLE schedules (
  id TEXT PRIMARY KEY,
  chore_id TEXT NOT NULL REFERENCES chores(id),
  kind TEXT NOT NULL CHECK (kind IN ('weekly', 'daily_interval', 'monthly')),
  interval INTEGER NOT NULL CHECK (interval BETWEEN 1 AND 999),
  anchor_date TEXT NOT NULL,
  monthly_day INTEGER CHECK (monthly_day BETWEEN 1 AND 31),
  valid_from TEXT NOT NULL,
  valid_until TEXT,
  created_at TEXT NOT NULL,
  CHECK ((kind = 'monthly') = (monthly_day IS NOT NULL)),
  CHECK (valid_until IS NULL OR valid_until >= valid_from)
);

CREATE UNIQUE INDEX one_active_schedule_per_chore
  ON schedules(chore_id) WHERE valid_until IS NULL;

CREATE TABLE schedule_weekdays (
  schedule_id TEXT NOT NULL REFERENCES schedules(id) ON DELETE CASCADE,
  weekday INTEGER NOT NULL CHECK (weekday BETWEEN 1 AND 7),
  PRIMARY KEY (schedule_id, weekday)
);

CREATE TABLE occurrences (
  id TEXT PRIMARY KEY,
  chore_id TEXT NOT NULL REFERENCES chores(id),
  schedule_id TEXT NOT NULL REFERENCES schedules(id),
  nominal_date TEXT NOT NULL,
  due_date TEXT NOT NULL,
  name_snapshot TEXT NOT NULL,
  description_snapshot TEXT,
  state TEXT NOT NULL CHECK (state IN ('pending', 'completed', 'skipped')),
  completed_at TEXT,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  UNIQUE (schedule_id, nominal_date),
  CHECK ((state = 'completed') = (completed_at IS NOT NULL))
);

CREATE INDEX occurrences_due_date ON occurrences(due_date);
CREATE INDEX schedules_chore_id ON schedules(chore_id);
```

Foreign keys are enabled for every connection. WAL mode and a bounded busy timeout are enabled. Each user action and each materialization range run in a transaction. SQL statements use parameters only.

### Migrations, recovery, and backups

Numbered, embedded, forward-only migrations run transactionally before the TUI opens. A database with a newer schema version is opened read-only only by `doctor`; the application refuses normal startup with an actionable message. Failed migrations roll back and leave the original version intact.

ChoreTUI does not silently recreate or overwrite an unreadable database. It reports the path, writes diagnostic detail to the log, and suggests `chore doctor`. Users can back up by closing the application and copying the database file; online backup and restore commands are future work. SQLite integrity checks are exposed through `doctor`.

## 9. Architecture

Dependencies point inward: TUI and CLI call application use cases; application code depends on domain interfaces; SQLite implements repository interfaces. The recurrence module is pure and reusable.

```text
src/
  main.rs                 Process entry, panic hook, exit codes
  lib.rs                  Public crate modules
  app/
    mod.rs                App state and command dispatch
    use_cases.rs          Mutating/query orchestration and transactions
  domain/
    chore.rs              Chore, schedule, occurrence types and validation
    week.rs               ISO week value object and statistics
    ports.rs              Repository and clock traits
  recurrence/
    mod.rs                Pure range expansion
  storage/
    mod.rs                Repository adapter
    sqlite.rs             Queries and transactions
    migrations.rs         Embedded migration runner
  config/
    mod.rs                Paths, TOML loading, validation
  tui/
    mod.rs                Terminal lifecycle and event loop
    model.rs              Selection and view state
    screens/              Board, editor, chore list, help
    widgets/              Shared rendering widgets
  cli.rs                  Argument parsing and doctor command
  diagnostics.rs          Tracing setup and panic report
tests/
  recurrence.rs
  storage.rs
  tui.rs
migrations/
  0001_initial.sql
```

The UI sends semantic commands such as `ToggleOccurrence(id)` instead of issuing SQL. Application use cases materialize required occurrences, enforce transactions, and return refreshed view data. A `Clock` trait makes “today” deterministic in tests. Repository traits are narrow and use domain values rather than SQL rows.

## 10. Technology decisions

| Area | Choice | Rationale |
|---|---|---|
| Language | Rust, current stable toolchain | Single portable binary, strong domain types, predictable performance, and mature terminal ecosystem. |
| TUI | Ratatui with Crossterm | Actively used retained-mode widgets with portable event and terminal control. |
| Persistence | rusqlite with bundled SQLite | Direct, explicit SQL and migrations without an ORM; bundled builds reduce host dependency issues. |
| Dates | `time` crate | Strong date arithmetic and ISO week support without introducing time zones into the domain. |
| CLI | clap derive | Clear help/version output and room for `doctor`. |
| IDs | uuid with v7 feature | Sortable stable identifiers independent of storage. |
| Config | serde + toml + directories | Typed configuration and correct platform/XDG paths. |
| Errors | thiserror for libraries, anyhow at process boundary | Typed recoverable domain errors plus contextual startup diagnostics. |
| Logging | tracing + tracing-subscriber, rolling file appender | Structured diagnostics kept out of the alternate-screen UI. |
| Tests | Built-in Rust test runner, proptest, insta where useful | Example and property tests for recurrence; small snapshots for stable rendering only. |

Dependencies use pinned compatible ranges in `Cargo.lock`. No async runtime is needed in MVP. Release builds deny compiler warnings in CI, run formatting and Clippy, and test on Linux, macOS, and Windows.

## 11. Configuration

The file is optional. Missing configuration uses defaults; a present but invalid file is an error rather than being silently ignored.

```toml
# ~/.config/choretui/config.toml
confirm_delete = true
show_completed = true
date_format = "iso"
```

Only these keys are supported in MVP:

| Key | Default | Meaning |
|---|---|---|
| `confirm_delete` | `true` | Require confirmation before soft deletion. |
| `show_completed` | `true` | Show completed occurrences on the board; hidden items still count in statistics. |
| `date_format` | `iso` | `iso` (`YYYY-MM-DD`) or `locale` for secondary date labels. |

Week start is not configurable because the product is explicitly ISO-week based. Default recurrence remains weekly in the editor and is not configurable until a real need is demonstrated. Unknown keys produce a warning for one release and are otherwise ignored to allow forward compatibility; invalid values and syntax block startup with file path and line/column when available.

## 12. CLI contract

The binary name is `chore`.

```text
chore              Open the interactive Weekly Board
chore doctor       Validate paths, configuration, database access, schema version,
                   foreign keys, and SQLite integrity without mutating user data
chore --help
chore --version
```

`doctor` prints a concise check table and exits `0` when healthy, `1` for a diagnosed user/data/configuration problem, and `2` for incorrect CLI usage. Interactive startup failures exit `1`. Headless CRUD is deferred.

## 13. Error handling

| Condition | Required behavior |
|---|---|
| Database path cannot be created/opened | Leave the terminal restored, show path and OS error, point to `chore doctor`, exit 1. |
| Database locked | Retry through the configured busy timeout, then show a non-destructive error; never discard changes. |
| Migration fails | Roll back migration, do not start TUI, preserve database, log migration and cause. |
| Database is corrupt | Do not recreate it; report integrity failure and backup guidance. |
| Configuration syntax/value invalid | Report file plus source location/key; do not continue with guessed defaults. |
| Unknown configuration key | Log and display a non-blocking warning once per startup. |
| Invalid recurrence | Reject at domain boundary and keep editor open with field-level explanation. |
| Terminal too small | Render the dedicated too-small view; recover automatically on resize. |
| Write fails after UI action | Keep prior view model state or reload from storage; show persistent error. |
| Unexpected panic | Restore alternate screen/cursor in a panic hook, write diagnostics to log, exit non-zero. |

All errors shown to users state what failed and what they can do next. Internal SQL and backtraces go to logs, not the normal screen. Secrets are not expected, but absolute paths and chore text are treated as personal data and are not sent anywhere.

## 14. Testing strategy

### Unit and property tests

- Domain validation for every field boundary and state transition.
- ISO week parsing, formatting, navigation, and year boundaries.
- Recurrence examples plus property tests asserting sorted, unique, in-range output.
- Weekly intervals across week-year boundaries; multiple weekdays; anchors midweek.
- Daily intervals over leap days and daylight-saving calendar dates.
- Monthly day 29–31 behavior in leap and non-leap years.
- Validity windows, disabled gaps, and no pre-anchor generation.
- Statistics including empty, future, missed, skipped, and late-completed weeks.

### Storage tests

Each test uses a temporary database and real migrations. Tests cover constraints, CRUD, schedule revision, disable/re-enable, soft delete, idempotent concurrent-style materialization, completion toggling, historical snapshots, transaction rollback, and upgrade from every supported schema fixture. Foreign-key and integrity checks are asserted.

### TUI tests

Application-state tests feed key events into a deterministic model with a fake repository and clock. Renderer tests use Ratatui's test backend at boundary sizes `39x13`, `40x14`, `69x20`, `70x20`, `109x20`, and `110x20`. Snapshot tests are limited to the board, editor validation, help, confirmation, and too-small view; semantic assertions verify selection and command dispatch.

### End-to-end and quality gates

A smoke test starts the binary against a temporary XDG tree, creates data through application use cases, opens a board frame, and runs `doctor`. CI requires `cargo fmt --check`, strict Clippy, tests, a release build, and dependency/license audit. Recurrence and storage tests must not depend on wall-clock time or user directories.

## 16. Implementation sequence

Implementation is split into repository issues rather than performed under #1:

1. Bootstrap Rust project, CI, diagnostics, and terminal lifecycle.
2. Implement domain values, validation, ISO week behavior, and weekly statistics.
3. Implement the pure recurrence engine and edge-case test suite.
4. Implement SQLite schema, migrations, repositories, and occurrence materialization.
5. Implement configuration loading and `doctor` CLI.
6. Implement Weekly Board state, responsive rendering, and navigation.
7. Implement completion toggle and consistent status/statistics refresh.
8. Implement Chore Editor and schedule revision use cases.
9. Implement Chore List, enable/disable, and soft deletion.
10. Implement help, confirmations, error surfaces, and end-to-end quality gates.

Each ticket should deliver a vertically testable boundary and may be merged independently in this order. Tickets may refine internal APIs, but changing product behavior or persistence semantics in this specification requires an explicit decision recorded in #1 or a follow-up architecture decision.

## 17. Acceptance baseline

The MVP is ready when a fresh installation can create recurring chores, reopen with persisted data, navigate ISO weeks, generate identical occurrence sets repeatedly, toggle completion, manage chore lifecycle, show correct weekly statistics, survive terminal resizes, and diagnose configuration/database failures without data loss. Historical occurrence names, due dates, and completion states must remain unchanged after future chore edits or deletion.
